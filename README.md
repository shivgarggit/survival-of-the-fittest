# Survival of the Fittest — public performance site

A static site that publishes the daily record of a 16-name, equal-weight, quarterly-reconstituted
equity strategy, benchmarked against major index funds. Rebuilt automatically after every US close.

No server. No database. No third-party price data is republished.

---

## What gets published

`site/portfolio.json` contains **only derived results**:

* index levels for the strategy and each benchmark, normalised to 1.00 at inception
* per-quarter summary rows: return, dividend yield, roster, entries and exits
* per-quarter component **returns** (percentages, never prices)

It does **not** contain a single ticker price. That distinction matters: in a static site the
data file is downloadable by anyone who opens devtools, so anything you put in it is published
whether or not the page displays it. Publishing index levels rather than prices is what keeps
this on the right side of your data provider's redistribution terms.

The visitor-facing interactivity survives intact because of one identity:

```
units += contribution / index
value  = units × index
```

Any starting amount, any contribution schedule, any date window — all reconstructable from an
index series alone. That is why the DCA controls work without shipping prices.

## One-time setup

1. **Create a GitHub repository** and push these files to it.

2. **Add your API token as a secret.**
   Settings → Secrets and variables → Actions → New repository secret
   Name it `TIINGO_TOKEN`. It is never written to the repo, never reaches the browser,
   and is masked in the Actions logs.

3. **Turn on Pages.**
   Settings → Pages → Source: **GitHub Actions** (not "Deploy from a branch").

4. **Run it once by hand.**
   Actions tab → *Refresh strategy data* → Run workflow. Takes 3–6 minutes on the first run.

5. Your site is live at `https://<user>.github.io/<repo>/`.

After that it rebuilds itself on the schedule and you never touch it again.

## Files

| Path | What it does |
|---|---|
| `.github/workflows/update.yml` | Nightly cron: fetch → build → deploy |
| `refresh_data.py` | Pulls prices, dividends and splits from Tiingo |
| `build_site.py` | Runs the backtest and emits the derived-only payload |
| `weights.xlsx` | Your quarterly roster — the only strategy input |
| `site/index.html` | The page |
| `site/app.js` | Engine and UI, runs client-side from the payload |
| `site/portfolio.json` | Regenerated by the workflow |

## Changing the strategy

Edit `weights.xlsx` and push. Add a row per quarter with start date, end date, and the weight
for each name. The next scheduled run picks it up. Nothing else needs to change.

To change the benchmark set, edit `BENCHMARKS` in `refresh_data.py` and the allow-list in the
leak-check step of the workflow.

---

## Schedule

Cron runs at 21:30 UTC, Monday to Friday — about 30 minutes after the US close in winter and
90 minutes in summer, since GitHub cron is always UTC and does not follow daylight saving.
Tiingo's end-of-day file is settled well before either, so the drift is harmless.

GitHub may delay scheduled runs by several minutes under load, and disables schedules entirely
on repos with no activity for 60 days. If the site goes stale, check the Actions tab first.

---

## The safety net

The workflow refuses to deploy if the payload looks wrong. It fails the build when:

* a price block appears in the payload
* an unexpected series name shows up
* the history is implausibly short
* series lengths disagree

A failed check leaves the previous version live rather than publishing something broken.

---

## Caveats worth keeping visible

The site states these on the page, and you should keep them there:

* **No costs are modelled.** No commission, spread, slippage or tax. A real account returns less,
  and the gap widens with contribution frequency.
* **Selection is an input, not an output.** The roster is a decision. If any name was chosen
  using information unavailable on the rebalance date, every figure is flattered.
* **UPRO is 3× leveraged** and holds an equal slot in most quarters, carrying roughly three times
  its weight in market exposure.
* **This is a backtest**, not a record of money actually managed.

## Licensing

Your provider's terms govern what you may publish. This design publishes your computed index
rather than their price feed, which is a far weaker redistribution claim — but confirm it with
them in writing before going public. That conversation is much cheaper before launch.
